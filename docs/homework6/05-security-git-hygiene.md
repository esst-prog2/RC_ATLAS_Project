# Review 5: Security and Git Hygiene

## Scope

Reviewed all tracked paths, Git history path metadata, active authentication and authorization boundaries, public initialization, CORS, storage/error responses, notification-provider configuration, runtime-file ignore rules, and tests. Protected untracked files were identified by name during preflight only; their contents were never read, moved, staged, modified, or removed.

## Method

- Inventoried tracked paths and searched history metadata for sensitive filename patterns.
- Used value-safe content searches that report only file/line references or high-confidence credential marker names.
- Traced public and protected routes through their authorization helpers.
- Inspected demo initialization, API response fields, CORS defaults, and notification adapter configuration.
- Verified the new runtime-backup ignore rule using a synthetic filename, not a protected file.

## Findings

### No high-confidence tracked secret material detected

No tracked private-key marker or common high-confidence access-token pattern was found. Matches for password, token, and API-key identifiers are predominantly model fields, request parameters, environment-variable names, and fictional disposable test/demo data. This is a static pattern review, not proof that repository history has never contained a secret.

### Timestamped runtime backups were not ignored

`.gitignore` covered `logitrack_data.json` and `logitrack_data.json.bak`, but not timestamped backup names generated by reliability workflows. The repository's original checkout has protected untracked files matching that shape. The correction adds `logitrack_data.json.*.bak`, preventing accidental future staging without reading or touching those files.

### Public demo initialization exposes credentials and local paths

`api/demo_routes.py:13` registers `/v1/demo/seed` without an authenticated actor. `services/demo_workspace.py:1048-1062` returns the storage target, an issued token, a default plaintext password, and all seeded fictional credentials. Although identities are documented as fictional, a network-reachable empty deployment could be initialized and controlled by its first caller. This requires coordinated API, deployment, and Studio changes and was not partially patched in this review.

### Internal storage paths are returned broadly

Multiple write responses return `saved_to`, including authentication and administration paths in `LogiTrackRC v4.4.py:6469-6525` and service responses in `services/reporting.py`, `services/dashboard_templates.py`, and `services/notifications.py`. Public API responses should use stable operation metadata rather than host filesystem paths.

### Wildcard CORS is the default

`LogiTrackRC v4.4.py:1331-1334` defaults `LOGITRACK_API_ALLOW_ORIGINS` to `*`. Credentials are disabled in wildcard mode, but an internet deployment should fail closed until explicit trusted origins are configured.

### Provider secrets and destinations may come from request bodies

`services/notifications.py:411-537` accepts SMTP, SendGrid, Twilio, and Meta credentials and destinations from request payloads, falling back to environment variables. Stored notification rule routing is also caller-overridable. Secrets and approved destinations need server-side configuration and policy enforcement before any external provider is enabled.

## Corrections

- Added the timestamped RC Atlas JSON backup pattern to `.gitignore`.
- Did not rewrite history, delete evidence, rotate credentials, or alter application behavior.

## Verification

Commands:

```text
git check-ignore --no-index -v logitrack_data.json.20991231T235959Z.synthetic.bak
py -m unittest -v security_tenant_stabilization_tests
git diff --check
```

The ignore check must identify the new `.gitignore` rule, and the existing tenant/security regression module must remain green.

## Remaining Risks

- Public demo initialization, response path disclosure, wildcard CORS, client-held bearer tokens, and provider request secrets remain release security issues.
- Static pattern matching cannot detect every encoded, fragmented, low-entropy, or previously removed secret. If real exposure is suspected, repository-owner review and credential rotation take precedence over history rewriting.
- Git history was not rewritten and no evidence was removed.
